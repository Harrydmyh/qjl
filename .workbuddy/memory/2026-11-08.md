## DeepSeek 品类判定的花费口径（用户问「什么情况会调、感觉花钱」）
- **唯一触发点**：`core._finish_fetch` 末尾 `_apply_llm_kind(all_out)`，即每次「刷新列表」拉完所有页之后跑一次。
  前端 6 个 `startFetch()` 全是用户主动点（按钮/回车/日历「拉取所选」/定向供应商回车），无自动刷新、无定时器。
- **只有缓存未命中的商品名才真发请求**（`norm_key` 去 emoji/标点后查 `data/kind_cache.json`）。
  实测 2026-11-08：948 个活动 / 948 个商品名 **全部命中**（缓存 3177 条）→ 再拉一次 0 次请求、0 成本。
- 实测 token：满批 120 个 = 输入 1743 + 输出 243；系统提示固定 333 tokens。
  按 flash 现价量级，一批约半分钱，全量冷启动（约 950 个新名 / 8 批）≈ 几分钱。日常只花在新活动上。

## 修：失败也写缓存 → 永久误判 0（既白花钱又判错）
- 原逻辑：模型返回位数不对/网络错误 → 劈半重试 → 仍失败就填 `0` **并写进缓存**，这些商品以后永远是「既非食品也非保健」。
- 现在：`except ValueError`（格式错，最可能救回来）才走 `_split_retry` 劈半一层（不递归，最坏 3 次请求）；
  `except Exception`（HTTP 401/402/429/超时）**不再重试**——同样的错再问一遍钱照样扣；失败的那批 **不写缓存**，下次重拉再判。
- 验证：HTTP 402 → 1 次请求、缓存 0 条；格式错 → 3 次请求、40 条全部写入；全失败 → 3 次、缓存 0 条。

## 修：server.py 启动被沙箱 shim 挡住
- `DATA_DIR.mkdir(exist_ok=True)` 在 WorkBuddy 的 sitecustomize shim 下抛 `FileExistsError: EEXIST`，服务起不来，curl 得到 502。
- 改成 `if not DATA_DIR.is_dir(): DATA_DIR.mkdir(parents=True, exist_ok=True)` —— 目录已在就完全不调 mkdir。
- 服务解释器：`/opt/homebrew/bin/python3`（默认 PATH 的 3.13 没 fastapi/requests）。
