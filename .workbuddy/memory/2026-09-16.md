## 修复「开团助手」活动列表筛选后右上角总数不变

- 文件：`index.html`（前端为原生 JS 单文件，逻辑全在页内 `<script>`）
- 根因：`renderActivities()` 里统计文案的条件写死了
  `filterText || catFilter !== 'all'`，漏掉了「分类多选 `selectedCats`」和
  「供应类型 `selectedUp`」两个筛选项 → 这两个筛选生效时列表变了、计数不变。
- 修法：
  - 新增 `catFilterActive()` / `upFilterActive()` / `anyFilterActive()` 统一判定"筛选是否生效"，
    列表与计数共用同一套判定，避免以后再漏。
  - 把筛选条件抽成单一谓词 `passFilters(a, ignoreCatChip)`，`getFiltered()` 与
    `getReopenCount()` 都基于它，保证「可复开」角标数量随筛选联动。
  - 计数文案：有筛选时显示「筛选后 X / 共 Y 条」，无筛选显示「共 Y 条」。
- 顺带修掉的同类 bug：
  - `setCatFilter()` 用入参 `val` 而非更新后的 `catFilter` 做高亮 → 取消筛选后按钮仍高亮。
  - `onCatAllChange()` 缺 `renderActivities()` → 勾"全部分类"列表不刷新。
  - 筛选无结果时提示语误导（原为"暂无数据，点击刷新列表拉取"），
    改为「没有符合当前筛选条件的活动」并给出"清除筛选"按钮（`clearAllFilters()`）。
  - 批量开团面板同样处理，`updateOpenStat(visible, total)` 增加筛选后计数。
- 验证方式：把 `<script>` 抽出做 `node --check`，再用**最小 DOM stub + 把测试代码拼进同一次 eval**
  的 harness 跑真实 677 条数据。
  ⚠️ 关键坑：`eval(src)` 里的 `let/const` 声明**不会**泄漏到外层作用域，
  所以测试代码必须**字符串拼接后一起 eval**（`eval(src + testCode)`），否则测试改的是另一个变量。
  结果：食品饮料 258/677、可复开 5/677（原为全局 21）、搜索"零食" 13 条，计数均同步。
- 本地服务：`/opt/homebrew/bin/python3 server.py`（端口 8765）。
  注意 managed python 3.13.12 没装 fastapi，系统 `/opt/homebrew/bin/python3` 才有。

## 排查：upStreamType 全为 0 + 复开逻辑梳理

### upStreamType —— 前端「供应类型」筛选是彻底失效的
- 实测两个接口的返回里**都没有 `upStreamType` 字段**：
  - 详情 `feed_base_search/query_list_by_act_ids`：32 个顶层字段中无此 key（3/3 命中不到）
  - feed 列表 `relation_help_sale_feed/list`：顶层只有 `{actId, foldActIds}`
- `core.parse_item()` 的 `item.get("upStreamType", 0)` → 恒取兜底值 0。
- 但 `upStreamTypeList` 作为**请求参数是真的生效的**（实测 `[2]` 与 `[3]` 返回的 10 条 actId 零重合）。
- 所以正确做法是**服务端筛选**：把 chip 选择传进 `/api/fetch` 的 `upstream_types`。
  而 `index.html` 的 `startFetch()` 里写死 `upstream_types: [2,3]`，chip 状态压根没传 → 双重失效。
- 分类同理：`firstCategoryIdList` 也是服务端参数，但前端发的是空数组，
  改用了 `CAT_KEYWORDS` 关键词猜分类（详情接口同样不含 categoryId）。

### 复开逻辑（core._finish_fetch）
三道判定，全通过才进 `reopen_raw`：
1. `hadHelpSale == True` —— 已被别人帮卖过
2. `actStat.totalOrderNum >= 1` —— 原活动至少成交 1 单
3. 距上次成功开团 ≥ 5 天（`open_log.json` 里按 **actId** 查，`(now-lo).days < 5` 则剔除）

新活动池：`not hadHelpSale and not isFollow`。两者互斥。
之后各自 `dedup_by_goods`（按 goodsId 集合去重，同款保留跟佣最高），
再标注 `bestActId` / `daysSinceOpen`，按 startTime 倒序。

发现的可疑点：
- **进度日志算术不平**：`removed_helped = total_raw - len(new_raw)` 把复开项也算成"被过滤掉"，
  而 `removed_dup` 只算新活动池 → 箭头链末端落在 `len(new_deduped)`，
  但状态行显示的是 `total_available`(= 新 + 复开)，有复开项时两者必然差 N 条。
- 5 天冷却依赖 `data/open_log.json`；**清空历史记录会让保护整体失效**。
- 冷却按 actId 匹配，但列表经过 `dedup_by_goods` 只留同款最优那条，**actId 会漂移 → 漏判**。
- 实测 21 条复开项的 `followEarning` **全部为 0**（新活动 656 条里只有 250 条为 0），
  复开项有 `earning`/`commissionPct` 但没有跟团佣金 → 列表那个「跟团佣金」列对复开无意义，
  按它排序也排不出名堂。复开更该看 `earning` / `helpSaleCount`。
- 实测 `data/` 下没有 open_log.json，所以 5 天规则当前处于"从未触发"状态。

## 已实施的修复（用户选择：供应类型勾选即重新拉取 / 复开问题全都修）

### 供应类型 → 服务端筛选（`index.html`）

- `onUpChange()` 更新 chip 后直接调 `startFetch()`；新增 `updateUpChip()`。

  也把它移出 `anyFilterActive()`——否则会显示"筛选后 N / 共 N 条"这种废话。
- `clearAllFilters()` 不再重置供应类型：它是「拉取范围」，不是「视图筛选」。
  视图筛选 = 分类多选 / 全部-新活动-可复开 / 搜索词。

### 进度日志算术（`core._finish_fetch`）
- 改为显式分桶：`total_raw / dropped / new_raw / reopen_raw / new_dup / reopen_dup
  / new_count / reopen_count / total_available`，并加了两个 assert 保证恒等式成立。
- `dropped` 才是真正丢弃的（帮卖过但无成交、或冷却中）；旧代码把复开项也算进了
  `removed_helped`，且 `removed_dup` 只统计新活动池 → 箭头链与"可用 N 条"必然差 reopen 数。

### 复开 5 天冷却改用 goodsId（`core.py` + `server.py`）

- `server.py` 开团成功时把 `goodsIds` 写进 open_log（从 activities.json 按 actId 反查）。
- `_finish_fetch` 同时维护 `last_opened`(actId) 与 `last_opened_goods`(goodsId)，
  判定取两者中**更晚**的时间 → 抗 actId 漂移；无 goodsIds 的旧日志仍按 actId 生效。
- 抽出 `REOPEN_COOLDOWN_DAYS = 5` 常量。
- 测试：合成 6 条数据覆盖"同款不同 actId"场景，9 项断言全过。
  ⚠️ `_finish_fetch` **不会**往队列里放 None 哨兵（那是调用方 server.py 的事），

## 批量开团：继承筛选 + 间隔浮动 + 服务端定时（用户选择：继承列表筛选 / 服务端定时）

### 排查结论：原来完全不继承，且有"看到5条开677个"的坑
- `renderOpenTab()` 里 `base = selectedIds.size ? 勾选的 : activities`（全部），
  活动列表的筛选**从不传递**；开团面板自带一套独立的 openCatFilter/openFilterText。
- 三个「全选」口径不一致：表头复选框=只选可见；列表右上「全选」`selectAllActs`=选**全部**；
  开团面板「全选」=只选可见。
- 最危险：开团面板筛选是 `display only`，筛出 5 条看着清爽，实际开的是 openIds 里的全部。
  `syncOpenTab()` 每次拉取后还会把 openIds 重置成全部。

### 修法（index.html）
- 新增 `openBase()`：有手动勾选 → 用勾选的；否则 → `getFiltered()`（继承列表筛选）。
- `renderOpenTab()` 里 `openIds = new Set(visible.map(a => a.actId))`——
  **面板内筛选直接决定将要开团的范围（所见即所开）**，改筛选就重算。
- `selectAllActs()` 改为只选 `getFiltered()`；按钮文案动态显示「全选筛选结果 (N)」。
- `syncOpenTab()` 先清理已不存在的 selectedIds 再重渲染。
- 新增 `delaySeconds()/jitterSeconds()/fmtSpan()/updateEta()`：
  「间隔数值 + 秒/分单位 + ±浮动秒」，实时显示「将开 N 个 · 平均间隔 X ±Y 秒 · 预计约 Z」。
- 开始前弹 confirm 列出将开数量/间隔/预计耗时/开始时间。
- ⚠️ 677 个 × 3 分 = **33 小时 51 分**，这个数字现在会直接显示在界面上。

### 间隔 + 随机浮动（core.batch_open_groups）
- 新签名：`batch_open_groups(config, act_ids, q, dry_run, delay, jitter=0.0, should_stop=None)`。
- `random.uniform(-jitter, jitter)` 叠加在 delay 上并 `max(0, ...)` 夹紧；
  等待循环每 0.25s 检查一次 `should_stop()` → **取消能立刻打断等待**，不用等满一轮。
- 等待前推 `{"type":"wait","seconds":w,"next_index":n}` 事件，前端显示"等待 N 秒后开下一条"。
- 实测：delay=1 ±0.3 → 3 段等待全落在 0.7~1.3；jitter=0 → 固定 0.5；
  取消时 2/5 条后 0.51s 就停（不会等满 2.5s）。

### 服务端定时任务（server.py）
- 把原来的 SSE `/api/open` **整个换成任务模型**（SSE 无法在关页面后接回进度）：
  - `POST /api/open/start` — `{act_ids, dry_run, delay, jitter, start_at}`，
    `start_at` 为本地 ISO 串（datetime-local 直接传），空=立即。
    校验：过去时间→400「开始时间已过」、格式错→400、锁占用→409。
  - `POST /api/open/cancel` — 置 `_job_cancel`，等待期和运行中都能中断。
  - `GET /api/open/status?since=N` — 返回快照 + 增量事件（前端每秒轮询）。
- `_job` 全局单任务状态：`id/state(scheduled|running|done|cancelled|failed)/total/index/ok/fail/
  current/next_wait/remaining/delay/jitter/events`，事件上限 3000 条。
- `_job_thread(job_id,...)`：先循环等待到点（每秒更新 remaining，可取消）→ 再执行；
  `finally` 里释放 `_open_lock`。`should_stop` 同时判 `_job_cancel` 和 `_job["id"] != job_id`。
- 前端 `reattachJob()` 在 init 时拉一次 status，只有 scheduled/running 才接管并开始轮询
  → 关掉页面再打开能接回进度和日志。
- 实测通过：立即执行、409 互斥、定时倒计时(12→11→9→6)、取消未开始、取消后自动执行、
  过去时间/非法格式 400。

⚠️ 复用坑：`nohup ... &` 启动的服务在 Bash 工具调用结束后会被杀掉，
必须用 `run_in_background: true`（否则下一个 curl 就 Connection refused）。
