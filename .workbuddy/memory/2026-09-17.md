# 2026-09-17

## 修复「开团报 不存在跟团活动」——根因是广场里混了两类活动

### 用户反馈
「筛选了以后开团的时候显示不存在跟团活动」

### 排查过程与结论（全部实测，非推断）
1. 该文案不在项目代码里（全项目搜过），是接口返回的 `msg`。
2. `for_follow`（取模板）不是元凶：19 条复开项**全测** + 抽样 30 条新活动，**49/49 返回 200**。
3. 错在 `release`（真正建团）。用「真实模板 + 空 actGoodsParams」探测校验顺序 → 先报 `5110 请添加商品`，够不到后续校验，所以只能真实开团验证。
4. **真开对照实验（决定性）**：
   - B 类（无跟团佣金）→ `ok=False`，0.6s，`开团失败: 活动未开启跟团功能，无法跟团`
   - A 类（有跟团佣金）→ `ok=True`，2.6s，newActId=2609151538144616（**真实创建了一个团**）
   - 再采样 6 条 B 类，**6/6 全部**同一句话 `活动未开启跟团功能，无法跟团`

### 两类的精确区别（接口字段可 100% 区分）
| | A 类 | B 类 |
|---|---|---|
| `activityType` | **150** | **10** |
| `ghType` | 20 / 105 | 10 |
| `ghViewType` | 10 | 0 |
| `followEarning` | 有值（1.14~399） | **null** |
| 能否 `release` 开团 | ✅ 能 | ❌ 不能 |
| 数量（今日 634 条） | 381 | 253 |
| `hadHelpSale` | 全 False | 19 条 True |
| 供货佣金 earning 中位 | 7.20 | 13.90 |
| 售价中位 | 39.90 | 59.90 |
| 被帮卖次数中位 | 4 | 8 |
| 来源 ghName 例子 | 🌟益能云天🌟 / 抬头见喜 | 🌙星辰大海①号 / 新小新家花园 |
| category | 全 new | 234 new + **19 reopen 全部** |

**业务解读**：A 类 = 品牌方/供货商**开放了跟团功能**的活动（有跟团佣金，能被跟团帮卖）；
B 类 = 普通团长自己开的团（一手货源、自家群），**未开启跟团功能**，广场会展示但你不能跟。

### 两个由字段直接推出的硬结论
1. **`upStreamTypeList` 与可开团性完全对应**（各抽 30 条验证）：
   - `[2]`「跟团活动」→ 30/30 activityType=10，**0/30 有跟团佣金** → **全部不能开团**
   - `[3]`「供货品牌」→ 29/29 activityType=150，**29/29 有跟团佣金** → **全部能开团**
   ⚠️ **index.html 里 2/3 的标签措辞要精确**（我最初说"标签是反的"，不准确）：
   - 值 3「供货品牌」**是准确的** —— 该类活动带 `supplier`/`isSupplyCompany`、ghType=20/105，确实是品牌/供货方的活动
   - 值 2 的问题**只是名字起错了**，不是两个互换 —— 该类 ghType=10、无 supplier 字段，是普通团长的活动，
     且不能跟团，「跟团活动」这个名字与"能不能跟团"的实际结果冲突
   - 接口**不返回类型**（`upStreamType` 在两个返回里都不存在），所以两个名字都是原作者按参数值猜的，
     官方叫法无从验证；界面上我写的"团长自营团"是**从数据反推的**，不是官方名
2. **「可复开」池子 100% 不可开团**：`hadHelpSale=True` 的 19 条**全部**落在 B 类。
   即 `_finish_fetch` 用 `hadHelpSale` 切分 new/reopen，而这个条件与可开团性**天然互斥** —— 
   复开功能在当前实现下永远开不出团，是产品级逻辑矛盾。

### 遗留待用户决定

- 真实测试多创建了 1 个团（newActId=2609151538144616），已告知用户可删。

### 复现用的诊断脚本要点
- 单条真开：`core.open_one_group(cfg, actId, dry_run=False)` → 返回 `(ok, new_id, name, err)`。
- 失败**会**写 `data/open_log.json`（已实测），所以「日志文件不存在」与「批量开团失败过」是矛盾的 —— 
  用户那次报错可能不是走 `/api/open/start` 这条流程，或记录被清过。此疑点到今天仍未解释通。

## 已实施的修复（用户选择：先修 1/2/3，不碰复开逻辑）

### core.py
- `parse_item` 新增 `hasFollowRelation`（= `bool(follow_earning)`，**必须区分 null 与 0**）
  和 `activityType`。这是"能否开团"的权威判据。

### index.html
- `canOpenAct(a)`：优先用 `a.hasFollowRelation`；**旧数据没有该字段时回退到 `followEarning > 0`**
  （已验证在本数据集 100% 等价）。`openableCount(list)` 配套。
- `.tag-noopen` + `tr.row-noopen{opacity:.55}` 样式；活动列表给不可开团的行打「不可开团」灰标签。
- `renderOpenTab`：`openIds = new Set(visible.filter(canOpenAct)...)`，新增 `openSkipped`
  记录跳过数；不可开团的行**仍显示但灰显 + checkbox disabled**（透明优先于隐藏）。
- `openToggleAll` / `openSelectAll` 必须 `if (el.disabled) return;`，否则会把禁用的行重新加进 openIds。
- `updateOpenStat` 增加「· 已跳过 N 个不可开团」。
- `updateSelUI` 里 `toOpenBtn` 文案改成按**可开团数**算，并在 title 里说明有多少会被跳过。
- `startOpen`：openIds 为空时区分两种情况给提示；confirm 里增加「已跳过 N 个」一行。
- 供应类型下拉标签改为事实化：`2 → 团长自营团 · 不可开团`、`3 → 品牌供货活动 · 可开团`，
  并加说明「只勾品牌供货活动拉到的就是 100% 可开团的」。
  **默认勾选保持不变**（改为只勾 [3] 会让"可复开"分类归零，属于动复开逻辑，用户没要）。

### 数据
- `data/activities.json` 回填了 `hasFollowRelation`（旧数据 0 条有），备份在 `activities.json.bak`。
  回填值用 `followEarning>0`（已验证 381/381、253/253 等价）。
  ⚠️ 真正的规则是 `followEarning != null`；若某项 followEarning 存在但 maxEarning=0，
  回填会误判。重新拉取一次就会写入真实的 `hasFollowRelation` 与 `activityType`。

### 验证结果（真实 634 条数据）
- 无筛选：列表 634 行 / 标记 253 / 开团面板 634 行 / 禁用 253 / **将开 381 · 跳过 253**
- 列表筛「可复开」：19 行全部标记 / **将开 0 · 跳过 19**（复开池 100% 不可开团）
- 旧数据回退路径与新字段路径结果完全一致

## 补充：新增「开团状态」三态筛选

- 活动列表工具栏加了一组 `#openableFilter`：`全部 / 可开团 / 不可开团`（`of-all` / `of-yes` / `of-no`），
  状态变量 `openableFilter`（'all'|'yes'|'no'），函数 `setOpenableFilter(val)`。
  与「全部/新活动/可复开」不同，**不做"再点一次取消"**（因为 all 是显式选项，更直观）。
- `passFilters()` 里**无条件**生效（不受 `ignoreCatChip` 影响），
  所以 `getReopenCount()`（可复开角标）也会跟着联动：筛「可开团」时角标自动隐藏（因为 0）。
- `anyFilterActive()` 与 `clearAllFilters()` 都已接入。
- **自动传导到批量开团面板**：`openBase()` → `getFiltered()`，所以列表设「可开团」后
  开团面板直接变成 将开 381 / 跳过 0；设「不可开团」则是 将开 0 / 跳过 253。
