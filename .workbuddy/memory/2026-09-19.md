## 新增「复团」工作流（按星期几拉取历史某天 + 按销量选品）

### 用户需求（口述澄清后）
做复团：从帮卖广场取「可以帮卖的那些」活动，但要的是**上周同一天 + 上上周同一天**（按星期几算，
比如今天周五就取上周五+上上周五）这两天的数据，按**销售数量降序**，同款去重（重合时留**单量更高**的），
然后开团。

### 前置验证（都做了实测，没有靠猜）
- feed 的 `filterFeedDTO.starTime/endTime` 支持**任意窗口** → 按单天拉取可行（每天一个窗口）
- 7~14 天前的活动 **100% 有跟团关系**（30/30、28/28），所以老活动**可以开团**
- 老活动**没有结束**：`endTime` 在 2027-01 ~ 2030-12，`startTime` 在过去
- 用户确认：**开团时间继承原活动**（不改 payload），所以 startTime 是过去式是接受的
- 用户确认：「底层商品库」= **就是列表内部同款去重**（同 goodsId 留一条），没有外部商品库

### core.py
- 抽出 `_fetch_window_pages(session, headers, gh_id, category_ids, upstream_types,
  start_ts, end_ts, q, label, batch=5)`：拉**单个时间窗口**的全部分页。
- `fetch_activities(..., dates=None)` 新增 `dates` 参数：给 `["YYYY-MM-DD",...]` 时
  **每个日期一个独立窗口**（当天 00:00 ~ 次日 00:00），逐窗口拉完再跨窗口去重 actId。
  没给 dates 就走原来的 `days_range` 单窗口逻辑。原实现按页码字典组织，重构成了列表收集。
- **`dedup_by_goods` 排序口径改了**：原来是 `total_earn`（跟团佣金）优先，
  现在改为 `(totalOrderNum, total_earn)` —— **单量优先，同量再比佣金**。
  ⚠️ 这是全局改动，会影响所有拉取（不只复团）。理由：列表主排序就是销量，去重口径必须一致。

### server.py
- `FetchParams` 新增 `dates: list[str] = []`，透传给 `core.fetch_activities(dates=...)`。

### index.html
- 「近 N 天」拆成**模式切换**：`最近 N 天` / `每周[周几] 往前 N 次`。
- `nthWeekdayBack(wd, weeksBack)`：**按周一起算一周**，weeksBack=1 → 上周该天，2 → 上上周。
  `rangeDates()` 返回 `["YYYY-MM-DD",...]`，`rangeHint` 实时显示"将拉取：09-11(五) · 09-04(五)"。
- 切到「每周」模式时**自动把排序切到 `totalOrders` 降序**（复团就是按销量挑品）。
- 新增 **「复团预设」按钮**（仅每周模式显示）：一键 = 供应类型只勾 [3] + 开团状态=可开团
  + 按总订单降序 + 重新拉取。
- 新增 CSS `.inline-sel` / `.inline-num`（chip 里的下拉和数字框）。

## ★★ 关键发现：feed 接口顶层 `keyword` 参数 = 全平台搜索（可定点拉供应商）

### 先纠正上一轮的一个错误结论

### ⚠️ 一个反直觉的数据结论（近 14 天，原始详情 943 条）
| 规则 | 条数 | 改前 | 改后 |
|---|---|---|---|
| A 帮卖过但 0 单 | 6 | 丢弃 | **保留** |

我开过的活动会翻成 isFollow=True 且 hadHelpSale 仍为 False → 落到 followed 桶，不走 reopen 冷却。
所以这条冷却规则在这份数据上**仍未被触发过**（合成数据里验证过它本身有效）。
- **A 类那 6 条 `followEarning` 全是 null → 不可开团**。保留后它们会以灰标签出现在列表里，

## ★ 修复「每周某天」的日期推算：会跳过本周已过的那天

用户问：今天周六(09-19)，选「周五 往前两周」为什么**不含昨天 09-18**？

### 根因
旧 `nthWeekdayBack` 锚定「**本周一**」`thisMonday`，再退 `7×weeksBack` 天，然后加星期偏移。
`weeksBack` 从 1 起算 → **永远从上周开始**，于是「本周一~今天之间已经过去的那天」被整个跳过：
- 今天周六选周五 → 旧算法给 09-11、09-04（**跳过了昨天的 09-18**）
- 今天周六选周一 → 旧给 09-07（跳过了本周一 09-14）

### 修复
改为「从今天往前找最近的该星期几（**严格早于今天**），再往前数 k-1 周」：
```js
let delta = (today.getDay() - wd + 7) % 7;
if (delta === 0) delta = 7;      // 今天正好就是该星期 → 从上周算起
d.setDate(today.getDate() - delta - 7 * (k - 1));
```
修正后（今天 09-19 周六）：
| 选项 | 修正前 | 修正后 |
|---|---|---|
| 周五×2 | 09-11 · 09-04 | **09-18 · 09-11** |
| 周五×1 | 09-11 | **09-18** |
| 周一×1 | 09-07 | **09-14** |
| 周六×2 | 09-12 · 09-05 | 09-12 · 09-05（不变） |
| 周日×2 | 09-13 · 09-06 | 09-13 · 09-06（不变） |

⚠️ 语义变化：**本周内已过去的那天现在算「往前 1 期」**。今天正好是该星期时不重复算今天。

### 另一个观察：服务端会往结果里插「推荐条目」
每次拉取都会混进几条 `effectTime` 恰好是 `06:00:00` 的条目（如拉 09-04/09-11 时混进
09-17 06:00 / 09-18 06:00 / 09-19 06:00 各 1~2 条），与所选窗口无关。
不是我们的 bug，但界面上会看到"窗口之外"的日期，属正常现象。
另外边界有极小时区溢出：拉 09-18 窗口会多出 3 条 09-19 06:00 的同类条目。

## ★★ 上面这次改动引入了一个崩溃，并暴露出**服务端锁永久泄漏**

### 崩在哪
`_item_sort_key` 里写了 `sum(g.get("earning", 0) or 0 ...)`，
而 **`earning` 恒为字符串**（实测 122/122 全是 str），还可能带区间 `'6.80~8.80'`
→ `int + str` → `TypeError`，`dedup_by_goods` 直接抛异常。

### 更严重的连带问题：`_fetch_lock` 永久泄漏
`/api/fetch` 的 `run_fetch()` 是这样消费内层线程的：
```python
threading.Thread(target=lambda: core.fetch_activities(...)).start()
while True:
    item = inner_q.get()      # ← 内层抛异常时，这里永远阻塞
    ...
finally:
    _fetch_lock.release()     # ← 永远执行不到
```
内层线程一崩，就再也不会往 `inner_q` 放东西，`inner_q.get()` 永久阻塞，
`finally` 不执行 → **锁永不释放 → 之后所有 `/api/fetch` 都 409「正在抓取中」**，
只能重启服务。实测就是这样卡了 5 分钟以上。
**同一个模式在 `/api/open/start` 的 `_job_thread` 里也存在**（会让 `_open_lock` 泄漏，
表现为开团按钮一直禁用、后续都 409）。

### 修复
1. `core.py` 新增 `_to_num(v, default=0.0)` 统一容错解析：
   处理 None / int / float / 数字字符串 / **区间字符串**（取上界）/ 非法值。
   - `_item_sort_key` 与 `parse_item` 都改用它。
   - 顺带修好一个老 bug：`parse_item` 原来 `float('6.80~8.80')` 会抛 ValueError 被吞掉
     → **区间佣金一直显示 ¥0.00**；现在取上界 8.80。
   - 注意 `followEarning` 可能是 dict **也可能是 null**，要 `isinstance(fe, dict)` 判断。
2. `server.py` 两处都改成「内层任务包一层，用 try/except/finally 保证一定往队列放结束哨兵」：
   - `/api/fetch` → `work()`：异常时放 `{"type":"error"}`，`finally` 放 `None`。
   - `/api/open/start` → `work()`：异常时 `_job_push` + `_job_update(state="failed")`，`finally` 放 `None`。

### 教训
**任何"内层线程 + 队列"的写法，内层必须保证无条件放结束哨兵**，
否则消费端会永久阻塞、持有锁不放。判断依据：`while True: q.get()` 一定要有
`try/except/finally` 兜底，或者用 `q.get(timeout=...)`。

### 重拉验证（09-14 + 09-07，[2,3]，605 条原始）
- 可用 575；去重 `新 443-28 | 已跟过 116-2 | 复开 46-0`

## ★★★ 会话级代理坑：所有请求报 ProxyError "Connection refused"

用户贴出开团报错：
```
ProxyError('Unable to connect to proxy',
  NewConnectionError("HTTPSConnection(host='127.0.0.1', port=63378):
                     [Errno 61] Connection refused"))
```

### 根因
**Agent 所在的 shell 环境里带着 `HTTP_PROXY/HTTPS_PROXY/http_proxy/https_proxy`，
指向 `http://127.0.0.1:<随机端口>`（会话级代理）**。我们从 shell 里启动 server.py 时，
这些变量被继承 → `requests` 默认 `trust_env=True` 会走它们 → **代理一失效，
所有出站请求全挂**。

- 端口是**每次会话都变**的：用户报错时是 63378，我排查时环境里已是 51478 —— 这本身就是证据。
- 时间线也吻合：那批开团 17:23~17:29 成功 4 个，**17:31 起连续失败**，
  正好卡在上一轮工具调用结束的时点。

### 修复
1. `core.make_session()`：
   ```python
   s.trust_env = False      # 忽略 *_PROXY / NO_PROXY / ~/.netrc
   s.proxies.clear()
   forced = os.environ.get("QJL_PROXY", "").strip()   # 需要走代理时的唯一入口
   if forced: s.proxies.update({"http": forced, "https": forced})
   ```
   （`core.py` 新增 `import os`）
2. `start.command` 里 `unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY all_proxy ALL_PROXY`
   + `export NO_PROXY=localhost,127.0.0.1,::1`，并在注释里写明用 `QJL_PROXY` opt-in。
3. 服务改用**剔除 *_proxy 的干净 env** 重启（PID 79772）。

### 验证
- 带代理变量的环境里 `make_session()` 直连成功（code 200）；`session.proxies == {}`。
- 显式把那死代理塞进 `session.proxies` → **精确复现**用户的 ProxyError（对照实验）。

### 通用教训
**给这个项目（以及任何"从 Agent shell 启动的本地服务"）启动进程时，
都要主动剔除 `*_proxy` 环境变量，或在代码里 `trust_env=False`。**
这类会话级代理端口会变、会失效，症状是"连不上本地代理"而不是"连不上目标站"，很容易误判。
