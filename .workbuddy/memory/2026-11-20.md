## token 过期与刷新链路（实盘抓包 Untitled.chlz，103 条请求）

用户给的 `.chlz` 是一段小程序首页的抓包，中间恰好撞上 token 过期。结论：

- **JWT 里只有 `uid` + `exp`，没有 `iat`、没有 refresh_token**。这次两枚 token 的 exp 分别是签发后**整 7 天**（13:38:26 过期 → 新 token 13:38:30 签发、11-27 13:38:30 过期）。
  - 与 MEMORY.md 原写的"48 小时"不一致。可能是不同登录入口给不同时长，未验证；先按"看到什么写什么"。
- **服务端严格校验，无宽限**：token exp 13:38:26，13:38:29.016 的请求立刻返回
  `{"code":403,"msg":"登录凭证不合法或已过期","success":false}`。这个 403 是唯一可靠的"token 死了"判据。
- **续期只有一条路**：`POST /user/login/wx_login_silence`
  body `{"code":"<wx.login 一次性 code>","scene":1005,"appid":"wx059cd327295ab444"}`
  → `{"code":200,"data":{"token":"<JWT>","uid":…,"firstLogin":0,"authorization":1}}`
  - 全抓包里**只有**这一个接口会吐 token，响应头也没有 set-token；**不存在**独立 refresh 接口。
  - 刷新请求自己还带着**旧的已过期** Authorization 头，说明服务端不校验它（按 code 换票）。
- **前端是"拦截 403 → 静默登录 → 重放"**：403 后 0.65s 调静默登录，0.34s 拿到新 token，原请求 0.02s 后重试成功，全程 1 秒内、用户无感。新 token 一到位，后面 16 条请求全用它。
- **对自动化的意义**：`code` 是小程序 `wx.login()` 的一次性票（绑 appid+scene，短时有效），脚本拿不到 → **这条自愈链路无法复刻**，token 过期仍然只能重抓。能给脚本用的只有 403 判据：命中就让任务自停/告警。
- 另有一条 `PUT /user/add_visit_num` 在登录后立刻发出（登录埋点）。13:38:16 那次 `EXCEPTION` 是服务端主动断开 HTTP/2（`Remote server closed the connection before sending response header`），跟 token 无关，下一轮 3 秒轮询就恢复了。

### 补充：code 是否可复用的实测（16:05）
拿抓包里那枚旧 code 重放 `wx_login_silence` → HTTP 401 `code=1230, msg=40029,invalid_code`。微信标准码，用过/过期即废。**确认：抓到的 code 只能当场用一次，缓存/重放都无效**。

### 结论：可落地的"自动换票"是**截票**，不是造票
小程序自己是"票源机"：token 到期撞 403 后 0.6s 内自动静默重登、用户无感。所以思路反转——
不要求脚本会生成 code，而是**让活着的小程序持续产出新 token，代理顺手截走写回 `data/config.json`**。
- 前提：HTTPS 解密（设备装 CA + 系统/网关代理）；小程序需保持存活（Mac 微信内打开，或一台闲置手机挂着），微信后台回收/机器睡眠是主要断点。
- 脚本侧只需 403 判据自停 + 等新票（轮询 config 的 token 变更 + `user_info` 验活），不要硬刷（风控）。
- 纯无人值守的另一条路是 hook `wx.login`（iOS Frida / 安卓 Xposed），成本远高于每周开一次小程序，不建议。
